# 1068 容灾监控进程修复

## 问题

2026-10-22 起，镜像改用 Alpine 签名包 `php83-pecl-swoole`（6.2.2-r0）。该包编译时启用了 io_uring，Swoole 的协程 `sleep`、文件读写钩子和 `waitpid` 都会走 io_uring：

- Docker 25 起默认 seccomp 策略禁止 `io_uring_setup`，创建失败时 Swoole 直接 `exit(1)`，不抛 PHP 异常；
- 即使放开 seccomp，该包在 6.7 以上内核上构建，启用了 io_uring futex，6.7 以下内核（如 Debian 12 的 6.1）同样会退出。

结果是 `php think dmtask` 打印“进程启动成功.”后约 1 秒退出，Supervisor 不断重启，容灾监控实际没有执行；后台只显示“未运行”，没有错误原因。镜像的健康检查只检查 PHP-FPM，因此容器仍显示 healthy。上游在 2026-07-30 的 `8fd7b3f`（修复docker镜像启动失败）中已改为源码编译，本分支在改用签名包时引入了回归。

## 修复

| 位置 | 修改 |
| --- | --- |
| `.github/docker/Dockerfile` | 不再安装 `php83-pecl-swoole`；从 PECL 下载 Swoole 6.2.3 源码，校验 SHA-256 后编译，不启用 io_uring，保留 sockets、mysqlnd、cURL 钩子、c-ares、brotli、zstd。运行库按 `scanelf` 结果安装，编译依赖随后删除。PHP 与其他扩展仍固定为 Alpine `8.3.36-r0`。 |
| `.github/docker/verify-runtime.php` | 构建和 CI 冒烟测试要求 Swoole 6.2.3、不含 io_uring，并在协程里实际执行 `usleep`、`Coroutine::sleep` 和文件读写（与 dmtask 使用的钩子一致）。原来的检查只测了 Channel，测不出这个问题。 |
| `app/command/Dmtask.php` | 若 Swoole 启用了 io_uring，启动前在子进程试运行一次协程 sleep；不可用时把原因写入“上次运行错误信息”并退出，不再静默崩溃。适用于自行安装 Swoole 的非 Docker 环境。 |
| `app/service/OperationsService.php`、`MaintenanceService.php` | 计划任务每分钟检查：存在启用的容灾任务，但 dmtask 心跳超过 5 分钟未更新时，通过“容灾切换通知”的渠道发一次告警（同一次停止只发一次，恢复后再停止会重新提醒）。 |
| `app/view/dmonitor/taskform.html`、`schedule/staskform.html` | 记录信息损坏或为空时，编辑页不再因 `JSON.parse` 报错而无法打开。 |

Swoole 6.2.3 相对 6.2.2 包含 cURL 钩子事件恢复、cURL 句柄释放和 AIO 线程饥饿修复，与上游 `29ba3cd` 一致。PECL 包的 SHA-256 为 `21dfa1c4a4a09f4d1cb4b154f7defdc91fbabafc8d44a77f8f618b9742c67304`，已与官方 Git 标签 v6.2.3 逐文件比对，除 PECL 打包时调整的测试文件外完全一致。

## 升级

拉取新镜像并重新创建容器即可，无数据库变更。之后打开「容灾监控」，运行状态应为“运行中”，容器日志中不再出现 `Iouring::Iouring(): Failed to initialize io_uring instance`。

## 验证

- `php tests/run.php`：35 个套件全部通过（新增 `monitor_watchdog_test.php` 6 项）；MySQL 集成测试 3 个套件在 MariaDB 10.11 上通过。
- 浏览器回归、55 个真实页面渲染及桌面/手机 110 次页面检查通过。
- 在 Docker 29、内核 6.1、默认 seccomp 的主机上：旧镜像的协程 sleep 以 io_uring 错误退出，放开 seccomp 后因 futex 要求同样退出；dmtask 的预检能识别并给出中文原因。
